# Configure a project: `downtrace init`

Part of the documentation of [`@downtrace/agent`](../README.md).

```sh
npx @downtrace/agent init
```

It reads the project in the directory it runs in — its `package.json`, the lockfile beside it (or above it, up to the top of its git repository, where a workspace keeps the one lockfile), its `next.config`, its `tsconfig.json`, its `nest-cli.json` and the entry the application starts from — and writes what the project needs. It asks for no token and no URL, asks no question, and makes no network request: locally there is no cloud. What it says of the token is what a person wiring production asks first: it is [safe to commit](../README.md#the-ingestion-token-is-safe-to-commit), with what whoever holds it can and cannot do, and how it is replaced. Installed with the project, `npx downtrace init` is the same command; where `@downtrace/agent` is not installed, `npx downtrace` is not (see [`downtrace check`](check.md)), and every command `init` prints is spelled for whether the project has the package.

| It looks for | Where | What it does with it |
|---|---|---|
| The test command | `scripts` of `package.json`: the first of `test:integration`, `test-integration`, `test:int`, `integration`, `test:e2e`, `test-e2e`, `e2e` and `test`, and npm's «no test specified» placeholder is no test | writes it to `downtrace.json` as `check.command`, run by the package manager that `packageManager` names or the lockfile is of — `pnpm-lock.yaml`, `yarn.lock`, `bun.lock` or `bun.lockb`, `package-lock.json` or `npm-shrinkwrap.json` — and npm without one: `npm run test:integration`, `pnpm test` |
| A framework whose routes are named by their templates | `express`, `koa`, `@strapi/strapi` (which runs on Koa), `fastify`, `hono`, `@hapi/hapi`, `next`, or NestJS's `@nestjs/platform-express` or `@nestjs/platform-fastify` (Nest serves through them) among the dependencies | says which |
| What the instrumentation observes inside a request | `pg`, `@prisma/adapter-pg`, `slonik` (which queries through `pg`: observed when that `pg` is the one at the application's root, as npm installs it), `pg-promise` (which queries through a `pg` of its own, found beside it), `postgres`, `@neondatabase/serverless` (0.9 and later), `@vercel/postgres` and `@prisma/adapter-neon` (which query through it), `mysql2`, `mysql`, `mariadb` (3 and later), `@prisma/adapter-mariadb`, `tedious`, `mssql`, `@prisma/adapter-mssql`, `better-sqlite3`, `@prisma/adapter-better-sqlite3`, `libsql`, `@libsql/client`, `sqlite3`, `mongodb` (6 and later), `mongoose` (8 and later), MikroORM's `@mikro-orm/postgresql`, `@mikro-orm/mysql`, `@mikro-orm/sqlite`, `@mikro-orm/better-sqlite`, `@mikro-orm/libsql` and `@mikro-orm/mongodb` (6 and later), `@prisma/client` (3.15 and later), `ioredis` and `redis` (node-redis, 5.12 and later) among the dependencies; outgoing HTTP always | says which |
| What it does not | among the dependencies, Postgres compiled to WebAssembly and run in the process: `@electric-sql/pglite`; the datastores and brokers reached through a protocol of their own: `oracledb`, `cassandra-driver`, `neo4j-driver`, `memjs`, `memcached`, `kafkajs`, `amqplib` and `amqp-connection-manager`, `@azure/service-bus` (AMQP 1.0), `mqtt` and `nats`; through a native binding: `couchbase`, `@confluentinc/kafka-javascript` and `node-rdkafka`; through gRPC, which runs on `node:http2` and not on the HTTP the instrumentation observes: `@google-cloud/firestore`, `@google-cloud/datastore`, `@google-cloud/spanner`, `@google-cloud/bigtable`, `@google-cloud/pubsub` and `firebase-admin` (its Firestore, and its Realtime Database over a WebSocket; its Auth, over HTTPS, is seen as calls). A client over HTTP — `@neondatabase/serverless`'s `neon()`, `@planetscale/database`, `@elastic/elasticsearch`, `@aws-sdk/client-dynamodb`, `@clickhouse/client` — is seen as calls, and BullMQ as the commands of its ioredis, and none of them is named here. And a Prisma driver adapter other than `@prisma/adapter-pg`, `@prisma/adapter-neon`, `@prisma/adapter-better-sqlite3`, `@prisma/adapter-mariadb` and `@prisma/adapter-mssql` (`@prisma/adapter-planetscale`, …), whose driver Prisma then queries through, `@prisma/client` before 7 whose schema (`prisma/schema.prisma` or `schema.prisma`) has the `prisma-client` generator on Prisma's own engine — what `prisma init` writes in 6.19 —, and `@prisma/client` before 3.15, `mongodb` before 6, `mongoose` before 8, `@mikro-orm/mongodb` before 6, `redis` before 5.12, `mariadb` before 3 and `@neondatabase/serverless` before 0.9, by the range declared: one that cannot reach that version (`^4.6.0`, `~5.11.9`, `5.1.0` of `redis`; `^0.8.1` of Neon's, since a caret keeps the minor on 0.x), and not one that lets the minor float (`^5.1.0`, `^5`), which may install it | says which, as `detected.unobserved`, and is configured all the same: `check` sees those requests and their calls, not that work, and a route whose work all goes there is not evaluated |
| A build that prunes what nothing imports | Next.js with `output: "standalone"` in `next.config` | writes [the hook above](../README.md#nextjs), in `src/` when the application is there, and as `instrumentation.js` in a project with no `tsconfig.json` |
| Where production starts | `@downtrace/agent` in `dependencies` (a dev dependency is not installed in production, and nothing is written for one); then, with `"type": "module"`, the `start` or `start:prod` script that runs `node`; for NestJS, the entry `nest-cli.json` names (`src/main.ts` by default); else the file `start` or `start:prod` runs with `node`, `nodemon`, `ts-node` or `tsx`, or `main` | writes the instrument file, which calls `init({ dsn: process.env.DOWNTRACE_DSN })`, and what loads it before anything else: beside the entry, `instrument.ts` with `import "./instrument";` as the entry's first line, or `instrument.js` with `require("./instrument");` (after a shebang, the leading comments and `"use strict"`); for ES modules, `instrument.mjs` at the root and `--import ./instrument.mjs` after the script's `node`. Not for Next.js, which has the hook above |

An integration suite comes before the unit one, and an end-to-end one — NestJS's `test:e2e`, which its CLI writes — after it, because `check` judges what each request ran: a run whose database is simulated observes nothing, and its routes are not evaluated. `init` installs nothing and does not write `routes`. What it edits of yours is only what loads the instrument file: the entry's first line, or the `node` of an ES module application's start script, every other byte of `package.json` left as it was. The instrument file reads `DOWNTRACE_DSN`, and without it the instrumentation does nothing: write your DSN in its place where the environment cannot be set, knowing that it then sends from every machine that runs the code, a developer's included, to the environment its token belongs to. As for `routes`: an Express, Fastify, Hono or Hapi application says which routes it has, and `check` reads them from it while the tests run; for another framework, declaring them is yours (`routes`, in [`downtrace check`](check.md#the-test-command-and-the-configuration)).

**Run it again whenever you like.** It writes `check.command` only where there is none: a `downtrace.json` that has one is left as it is, byte for byte, and one without it gets the command and keeps every other key, inside `check` and outside it. The hook is written only where the project has no `instrumentation` file at the root or in `src/`; the instrument file only where there is none, and the line that loads it only where nothing loads it yet.

When something cannot be detected or done, it says what and what to do instead, writes what it could, and ends with 1:

| Code | What it means, and what to do |
|---|---|
| no-package-json | There is no `package.json` where it runs: run it at the root of the Node.js project, and in a monorepo in the directory of the service. |
| no-framework | None of the frameworks above. In a monorepo, run it in the directory of the service. Elsewhere `check` still compares the runs: the instrumentation observes every request Node's server receives and names its route by the shape of its path (see [How routes are named](routes.md)). A request a test hands the application with no server listening, through a helper of the framework's own, is not observed. |
| no-test-command | None of the scripts above. Give `check` a command that sends requests to the routes with their real dependencies: a test script, or a walk of the routes — a script that starts the application, sends a request to each route and stops it — in `downtrace.json` or after `--`. |
| not-a-repository | No git repository holds the project, and `check` compares the working tree against a commit. |
| not-installed | The build prunes and `@downtrace/agent` is not a dependency, so a hook that imports it would break the build: install it and run `npx downtrace init` again. |
| instrumentation-exists | The project has a hook that does not load the instrumentation. It is not touched; add the `if` and its `import` of [the hook](../README.md#nextjs) inside its `register()`. |
| module-resolution | `tsconfig.json` sets `moduleResolution` to `node`, `node10` or `classic`, which cannot resolve `@downtrace/agent/register`: set it to `bundler`, `node16` or `nodenext`, and run it again. |
| no-entry | Production starts from a file `init` cannot edit: none found, or JavaScript compiled from TypeScript, whose source it cannot tell. Nothing is written for it. Write `instrument.js` beside the file the application starts from (`instrument.ts` beside its TypeScript source), with `init({ dsn: process.env.DOWNTRACE_DSN })`, and load it on that file's first line: `require("./instrument");`, or `import "./instrument";` in TypeScript. |
| no-start-script | An ES module application with no `start` or `start:prod` script that runs `node`: `instrument.mjs` is written, and nothing loads it yet. Start the application with `node --import ./instrument.mjs <entry>`, in a script, a Dockerfile's `CMD` or `NODE_OPTIONS`: an ES module's imports are all loaded before its first line runs. |

The exit status: **0 configured**, **1 something could not be detected or done**, **2 a file it reads could not be read** — a `package.json` that is not JSON or not shaped as one (`bad-package-json`), a `downtrace.json` that `check` would refuse (`bad-config`; it is the person's, and not rewritten), or a file the system would not give (`io-error`) — and nothing was written. `--json` prints one object for a coding agent, `schema: "downtrace-init/1"`: `status` (`configured`, `incomplete` or `failed`), `project`, `detected` (the package manager, the frameworks, the observed packages, the test script and its command, and `bundler`), `command` (what `check` runs now: the one `init` wrote, or the one a person had put there), `files` (each `created`, `updated` or `unchanged`), `missing` (each with a `code`, a `message` and `advice`), `failure`, `next`, the command to run next, `instrument`: the instrument `file`, what loads it (`loadedBy`, the entry or `scripts.start`), and `skipped`, why there is none on purpose; null for Next.js; and `token` (what the text says of the ingestion token: `safeToCommit`, `can`, `cannot` and `replace`).
